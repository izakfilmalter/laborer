## Issue 10: Replay input guard — COMPLETED

### Summary
Added replay input guards to both the server-side data channel and the
client-side renderer to prevent user input, resize events, and flow control
ack messages from corrupting terminal state during replay. VS Code implements
this as `_inReplay = true` on both sides — we now have equivalent protection.

The guard operates at three layers:
1. **Server-side (data channel)**: An `isReplayingToRenderer` flag is set when
   the replay payload is sent and cleared after `replayComplete`. During this
   window, all incoming renderer messages (input keystrokes, ack messages) are
   dropped by the `messageHandler`.
2. **Client-side (send guard)**: The `send()` function in
   `useTerminalMessagePort` checks a `replayStatusRef` and no-ops when
   `replaying`. Flow control acks are also suppressed during replay.
3. **Client-side (resize guard)**: The `ResizeObserver` callback in
   `TerminalPaneRenderer` checks a `replayStatusRef` and skips resize
   processing during replay. The post-replay fit (already guarded by
   `replayStatus !== 'complete'`) handles the initial resize after replay.

### Changes
- `packages/terminal/src/services/terminal-data-channel.ts`:
  - Added `isReplayingToRenderer` flag, set to `true` before `encodeReplay()`
    and cleared after `encodeReplayComplete()`
  - Added early return in `messageHandler` when `isReplayingToRenderer` is true,
    dropping all incoming renderer messages during the replay window

- `apps/web/src/hooks/use-terminal-messageport.ts`:
  - Added `replayStatusRef` to track replay status for memoized callbacks
  - `send()` no-ops when `replayStatusRef.current === 'replaying'`
  - `maybeAck()` suppresses ack messages during replay
  - `handleControlMessage` syncs `replayStatusRef` alongside React state
  - Effect cleanup resets `replayStatusRef` on remount

- `apps/web/src/panes/terminal-pane.tsx`:
  - Added `replayStatusRef` in `TerminalPaneRenderer` synced from props
  - `ResizeObserver` callback skips resize when `replayStatusRef.current ===
    'replaying'`

- `packages/terminal/test/terminal-data-channel.test.ts`:
  - Added test: replay and replayComplete sent in correct order with input

  - Added test: input resumes correctly after replayComplete

## Issue 11: rawReviveBuffer optimization — COMPLETED

### Summary
Implemented the rawReviveBuffer optimization to avoid cumulative data loss from
repeated serialize/deserialize cycles on idle terminals. When a terminal is
revived from persisted state, the original raw screen state is stored alongside
the headless xterm instance. If the terminal remains idle (no user input or
renderer-initiated resize), `getScreenState()` returns the stored raw buffer
instead of re-serializing through the xterm serialize addon. This bounds
serialization degradation to one cycle per user interaction epoch.

The optimization tracks per-terminal interaction state through three phases:
- `'none'` — Terminal freshly created or recovered, no interaction yet
- `'replay-only'` — Revived replay sent to renderer, but user never typed/resized
- `'session'` — User has directly interacted; raw buffer freed, live serialize used

### Changes
- `packages/terminal/src/lib/headless-terminal.ts`:
  - Added `TerminalInteractionState` type (`'none' | 'replay-only' | 'session'`)
  - Extended `HeadlessTerminalState` with `interactionState` and `rawReviveBuffer`
  - Updated `getScreenState()` to return raw buffer for idle terminals
  - Added `setRawReviveBuffer()` — stores raw buffer on terminal revival
  - Added `freeRawReviveBuffer()` — frees buffer and transitions to `'session'`
  - Added `markReplayed()` — transitions from `'none'` to `'replay-only'`
  - Updated `HeadlessTerminalManager` interface with three new methods

- `packages/terminal/src/services/terminal-manager.ts`:
  - Added `freeRawReviveBuffer`, `setRawReviveBuffer`, `markReplayed` to
    `TerminalManager` interface and wired through to headless manager
  - Added `freeRawReviveBuffer()` call in `write` handler (user input)
  - Added `freeRawReviveBuffer()` call in `resize` handler (renderer resize)

- `packages/terminal/src/services/terminal-data-channel.ts`:
  - Added `markReplayed()` call after sending revived replay event to renderer

- `packages/terminal/src/utility-main.ts`:
  - Added `setRawReviveBuffer()` call during terminal restoration with the

## Issue 3: FinalTerm 133 command detection fallback — COMPLETED

### Summary
Added OSC 133;B (command start) and OSC 133;D (command finished) handling as a
command detection fallback for shells that only emit FinalTerm sequences (e.g.,
powerlevel10k configurations that emit OSC 133 but not OSC 633). This enables
basic command tracking for any shell with FinalTerm protocol support.

The implementation follows VS Code's priority scheme: once any OSC 633 sequence
is seen, the shell integration status permanently becomes `'vscode'` and
FinalTerm 133;B/D stop creating commands. However, 133;A (prompt start) and
133;C (command executed) continue to fire prompt state callbacks regardless of
633 presence.

FinalTerm-detected commands have:
- `commandLineConfidence: 'low'` (FinalTerm doesn't include command text)
- `isTrusted: false` (no nonce verification possible)
- Empty `command` string (command text unavailable)
- Full positional metadata from xterm markers (same as 633 commands)

### Changes
- `packages/terminal/src/lib/headless-terminal.ts`:
  - Added `ShellIntegrationStatus` type (`'none' | 'finalterm' | 'vscode'`)
  - Added `shellIntegrationStatus` field to `HeadlessCommandState`
  - Set `shellIntegrationStatus = 'vscode'` in `handleVsCodeOscSequence()` when
    any 633 sequence is received
  - Added `handleFinalTermPromptStart()` — 133;A handler: fires prompt callback
    (idle) and records pending prompt start line for FinalTerm fallback
  - Added `handleFinalTermCommandStart()` — 133;B handler: creates in-flight
    command with low confidence, only when no 633 sequences seen
  - Added `handleFinalTermCommandExecuted()` — 133;C handler: fires prompt
    callback (running) and records executedLine/executedX on in-flight command
  - Added `handleFinalTermCommandFinished()` — 133;D handler: finalizes command
    with exit code and end marker, only when no 633 sequences seen
  - Added `handleFinalTermOscSequence()` — dispatcher that parses the 133
    marker and delegates to the per-marker handlers
  - Refactored OSC 133 handler registration in `create()` to always register
    (even without `onPromptState`), delegating to `handleFinalTermOscSequence`

- `packages/terminal/test/headless-terminal.test.ts`:

Buffer marks are tracked as `{ line, id?, hidden? }` entries in the
`HeadlessCommandState.bufferMarks` array, fed by three OSC sources:
- **OSC 633;SetMark** — VS Code's mark sequence with optional `Id=<string>`
  and `Hidden` parameters
- **OSC 633;P Task** — Creates a mark at the current cursor line and sets
  `disableCommandStorage` for task terminals

Marks serialize into `SerializedCapabilityStore.bufferMarks` and flow through
persistence and the data channel to the renderer. Hidden marks are tracked
internally but flagged for future rendering decisions (tracked but not
rendered by the gutter UI).

## Issue 7: ShellEnvDetection + indicator — COMPLETED

### Summary
Added `ShellEnvDetection` capability to the capability store with nonce-verified
trust tracking. The implementation mirrors VS Code's `ShellEnvDetectionCapability`
class, supporting two modes of environment reporting:

1. **OSC 633;EnvJson** — Replaces the entire environment from a single JSON
   payload with a mandatory nonce for trust verification.
2. **OSC 633;EnvSingle*** — Transaction-based individual variable operations:
   - `EnvSingleStart` begins a transaction (optionally clearing existing env)
   - `EnvSingleEntry` adds a key-value pair to the pending transaction
   - `EnvSingleDelete` removes a key from the pending transaction
   - `EnvSingleEnd` commits the transaction

Trust uses logical AND across all operations in a batch — if any operation
in a transaction is untrusted (nonce mismatch or missing), the entire batch
becomes untrusted. This matches VS Code's trust propagation semantics.

The environment state serializes into `SerializedCapabilityStore.shellEnvDetection`
as `{ env: Record<string, string>, isTrusted: boolean }` and flows through all
layers: headless terminal tracking, persistence serialization, data channel
replay, and renderer-side types.
