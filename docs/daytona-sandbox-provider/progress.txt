## Issue 8: SandboxProvider Effect interface definition

Status: COMPLETE
Date: 2026-04-07

### Changes made:
- Created new file packages/server/src/services/sandbox-provider.ts
- Defined SandboxProvider Effect Context.Tag with identifier '@laborer/SandboxProvider'
- Interface includes 8 methods:
  createSandbox(params: CreateSandboxParams) => Effect<void, RpcError>
  destroySandbox(workspaceId: string) => Effect<void, RpcError>
  pauseSandbox(workspaceId: string) => Effect<void, RpcError>
  resumeSandbox(workspaceId: string) => Effect<void, RpcError>
  getPreviewUrl(workspaceId: string, port: number) => Effect<string, RpcError>
  spawnTerminal(workspaceId: string, opts?: TerminalOpts) => Effect<TerminalHandle, RpcError>
  reconcileState() => Effect<void>
  checkAvailability() => Effect<ProviderStatus>
- Defined CreateSandboxParams type with workspaceId, branchName, projectName, worktreePath,
  devServerConfig (matching ResolvedDevServerConfig shape), and optional onReady callback
- Defined TerminalOpts type with optional command, autoRun, cols, rows
- Defined TerminalHandle type with id, workspaceId, command, status — matches existing
  TerminalRecord shape from terminal-client.ts for drop-in compatibility
- Defined ProviderStatus type with available boolean + optional error string — matches
  existing DockerStatus shape from docker-detection.ts
- All types exported for use by both Docker and Daytona implementations

### Design decisions:
- CreateSandboxParams.devServerConfig uses concrete types (not ResolvedValue<T> wrappers)
  since providers need the resolved values, not the provenance metadata
- TerminalHandle intentionally matches TerminalRecord to minimize adapter code in Issue 9
- ProviderStatus intentionally matches DockerStatus to minimize adapter code in Issue 9
- No layer defined on SandboxProvider — implementations provide their own layers
- reconcileState and checkAvailability have no error channel (Effect<void> / Effect<ProviderStatus>)
  since failures are handled internally (logged, not propagated)

- Pure adapter layer: no new behavior introduced, existing Docker flow unchanged
- ContainerService continues to emit v1.Container* events internally (both v1 and v2
  materializers write to the same sandbox* columns, so this is correct)
- Full migration of Docker path to v2 events deferred to Issue 10 (WorkspaceProvider refactor)
- Uses Layer.effect (not Layer.scoped) since no finalizers are needed — cleanup is handled
  by the underlying services (ContainerService, TerminalClient)
- createSandbox looks up project repoPath from LiveStore for lockfile detection, falling
  back to worktreePath if project lookup fails
- getPreviewUrl returns full http:// URL with port appended

## Issue 11: Daytona SDK client Effect service (thin wrapper)

Status: COMPLETE
Date: 2026-04-07

### Changes made:
- Installed `@daytonaio/sdk` (v0.161.0) as a dependency of `packages/server`
- Created new file `packages/server/src/services/daytona-client.ts`
- Defined `DaytonaClient` Effect `Context.Tag` with identifier `@laborer/DaytonaClient`
- Service interface exposes 7 Effect-wrapped SDK operations:
  - `create(params, options?)` — create sandbox from image
  - `createFromSnapshot(params, options?)` — create sandbox from snapshot
  - `get(sandboxIdOrName)` — get sandbox by ID or name
  - `list(labels?, page?, limit?)` — list sandboxes with optional label filter
  - `start(sandbox, timeout?)` — start a stopped sandbox
  - `stop(sandbox)` — stop a running sandbox
  - `delete(sandbox, timeout?)` — permanently delete a sandbox
- Also exposes `snapshot` (Daytona SnapshotService) and `raw` (Daytona SDK instance) for direct access
- `DaytonaClient.layer` reads `DAYTONA_API_KEY`, `DAYTONA_API_URL`, `DAYTONA_TARGET` from env
  and constructs the `Daytona` SDK instance. Dies if `DAYTONA_API_KEY` is not set.
- Error mapping: SDK errors -> `RpcError` with distinct codes:
  - `DaytonaNotFoundError` -> `DAYTONA_NOT_FOUND`
  - `DaytonaRateLimitError` -> `DAYTONA_RATE_LIMIT`
  - `DaytonaTimeoutError` -> `DAYTONA_TIMEOUT`
  - Other errors -> `DAYTONA_ERROR` / `DAYTONA_UNKNOWN`
- Exported type aliases for consumers: `DaytonaSandbox`, `DaytonaPaginatedSandboxes`,
  `CreateSandboxFromImageParams`, `CreateSandboxFromSnapshotParams`

### Design decisions:
- `PaginatedSandboxes` is not exported from `@daytonaio/sdk` public API, so we use
  `Awaited<ReturnType<Daytona['list']>>` as the `DaytonaPaginatedSandboxes` type alias
- Layer uses `Effect.die` (defect, not typed error) for missing API key since this is
  a configuration error that should crash early, not be handled by callers
- Each SDK method wrapped with `Effect.fn` for call-site tracing
- `snapshot` sub-service exposed directly (not wrapped) since snapshot operations are
  varied and wrapping each adds minimal value
- `raw` Daytona instance exposed for cases needing direct SDK access (e.g., sandbox
  instance methods like `createSshAccess`, `getPreviewLink`)
- No test files added — the DaytonaClient layer requires a real API key to construct.
  Integration tests (Daytona-required) will be added as part of downstream issues.

## Issue 13: DaytonaSandboxProvider — create sandbox

Status: COMPLETE
Date: 2026-04-07

### Changes made:
- Created new file `packages/server/src/services/daytona-sandbox-provider.ts`
- Defined `DaytonaSandboxProvider` as a `Context.Tag` that produces a `SandboxProvider` value
- `DaytonaSandboxProvider.layer` depends on `DaytonaClient` and `LaborerStore`
- All 8 `SandboxProvider` interface methods implemented:
  - `createSandbox`: Core Daytona integration — creates a cloud sandbox for a workspace
    - Determines image from `devServer.image` or uses Daytona default (via `createFromSnapshot`)
    - Creates sandbox via `DaytonaClient.create()` with TypeScript language, labeler labels
      (`laborer-workspace-id`, `laborer-project`, `laborer-branch`), auto-stop (15min),
      auto-archive (7 days), auto-delete disabled (-1)
    - Reports progress via `v2.SandboxSetupStepChanged` events (`creating-sandbox`, `starting-sandbox`)
    - Commits `v2.SandboxStarted` event with `sandboxProvider: "daytona"`
    - Invokes `onReady` callback after successful creation
  - `destroySandbox`: Looks up sandbox from LiveStore, calls `DaytonaClient.get()` then
    `DaytonaClient.delete()`, handles already-destroyed (404) gracefully, commits `v2.SandboxStopped`
  - `pauseSandbox`: Calls `DaytonaClient.stop()`, commits `v2.SandboxPaused`
  - `resumeSandbox`: Calls `DaytonaClient.start()`, commits `v2.SandboxResumed`
  - `getPreviewUrl`: Calls `sandbox.getPreviewLink(port)` via SDK, returns URL string
  - `spawnTerminal`: Stub returning `NOT_IMPLEMENTED` error (Issue 16)
  - `reconcileState`: Stub logging debug message (Issue 20)
  - `checkAvailability`: Calls `DaytonaClient.list(limit=1)` as connectivity check

### Design decisions:
- When `devServer.image` is null, uses `DaytonaClient.createFromSnapshot` (no snapshot param =
  Daytona default image which includes Node 22, bun, git, Claude Code, OpenCode, Codex)
- When `devServer.image` is set, uses `DaytonaClient.create` with `CreateSandboxFromImageParams`
- `sandboxUrl` column stores the sandbox ID (Daytona preview URLs are constructed per-port
  via `sandbox.getPreviewLink()`)
- `sandboxImage` stored as `'daytona-default'` when using the default image
- Destroy is best-effort: logs warnings on errors but doesn't fail the destroy
- Destroy is idempotent: handles already-destroyed sandboxes gracefully (catches 404)
- Pause/resume call Daytona stop/start respectively (Daytona terminology)

### Tests added (9 tests in packages/server/test/daytona-sandbox-provider.test.ts):

- createSandbox: calls `createFromSnapshot` when `devServer.image` is null (Daytona default)
- createSandbox: invokes `onReady` callback after creation
- createSandbox: sets labels with workspace ID, project name, and branch name
- destroySandbox: deletes sandbox and commits `SandboxStopped`
- destroySandbox: handles already-destroyed sandbox gracefully (NOT_FOUND)
- pauseSandbox: stops sandbox and commits `SandboxPaused`
- resumeSandbox: starts sandbox and commits `SandboxResumed`
- checkAvailability: returns available when `DaytonaClient.list` succeeds

### Test approach:

## Issue 23: End-to-end integration — Daytona workspace creation flow

Status: COMPLETE
Date: 2026-04-07

### Changes made:

#### New file: `packages/server/src/services/sandbox-provider-router.ts`
- Created `SandboxProviderRouter` — a routing `SandboxProvider` layer that dispatches
  sandbox operations to either `DockerSandboxProvider` or `DaytonaSandboxProvider`
  based on per-workspace configuration
- Routing logic:
  - `createSandbox`: reads `devServerConfig.provider` from the params to dispatch
  - All other methods (`destroySandbox`, `pauseSandbox`, `resumeSandbox`, `getPreviewUrl`,
    `spawnTerminal`, `setAutoStopInterval`): looks up the workspace's `sandboxProvider`
    column in LiveStore to determine which provider to use
  - `reconcileState`: runs both providers' reconciliation (Docker events + Daytona polling)
  - `checkAvailability`: returns the Docker provider's status (the primary provider)
- `SandboxProviderRoutedLayer`: Composed layer that provides `SandboxProvider` and
  `DockerSandboxProvider` by:
  1. Building `DockerSandboxProvider.layer` (always succeeds)
  2. Optionally building `DaytonaSandboxProvider.layer` via `DaytonaClient.layer` —
     catches `DaytonaClientMissingKeyError` when `DAYTONA_API_KEY` is not set
  3. Building the routing layer that dispatches between the two
- When Daytona is not available, requests routed to it return a clear
  `DAYTONA_UNAVAILABLE` error with guidance to set `DAYTONA_API_KEY`
- Uses `Effect.serviceOption(DaytonaSandboxProvider)` to optionally resolve the
  Daytona provider — no crash if it's not in the context

#### Modified: `packages/server/src/services/docker-sandbox-provider.ts`
- Changed `DockerSandboxProvider.layer` to provide its own `DockerSandboxProvider`
  tag instead of the abstract `SandboxProvider` tag
- Changed `SandboxProvider.of(...)` to `DockerSandboxProvider.of(...)` in the return value
- Changed `SandboxProvider` import to type-only import (no longer used as a value)
- No behavioral changes — the adapter still wraps the same Docker services

#### Modified: `packages/server/src/services/daytona-sandbox-provider.ts`
- Changed `DaytonaSandboxProvider.layer` to provide its own `DaytonaSandboxProvider`
  tag instead of the abstract `SandboxProvider` tag
- Changed `SandboxProvider.of(...)` to `DaytonaSandboxProvider.of(...)` in the return value
- Changed `SandboxProvider` import to type-only (no longer used as a value)
- No behavioral changes — the Daytona implementation is unchanged

#### Modified: `packages/server/src/services/daytona-client.ts`
- Changed `DaytonaClient.layer` from `Effect.die` to `Effect.fail` with a typed
  `DaytonaClientMissingKeyError` when `DAYTONA_API_KEY` is not set
- Added `DaytonaClientMissingKeyError` class extending `Data.TaggedError` with
  a descriptive message
- Layer type signature updated: `Layer.Layer<DaytonaClient, DaytonaClientMissingKeyError>`
- This allows the `SandboxProviderRouter` to catch the error and gracefully degrade
  when Daytona credentials are not configured, instead of crashing the service stack
- Exported `DaytonaClientMissingKeyError` for use by the router

#### Modified: `packages/server/src/services/workspace-provider.ts`
- Updated `startSandbox` to allow null `devServer.image` for Daytona workspaces:
  - Previously: rejected all workspaces with `devServer.image === null`
  - Now: only rejects when `provider !== 'daytona'` and `image === null`
  - Daytona uses a default image (Node 22, bun, git, Claude Code, OpenCode, Codex)
    when no explicit image is configured

- Replaced `DockerSandboxProvider.layer` with `SandboxProviderRoutedLayer` in
  `DeferredServiceStack`

#### Modified: `packages/server/test/rpc/test-layer.ts`

  `DeferredServiceStack`
- Updated imports and comments accordingly

#### Modified: `packages/server/test/workspace-destroy-origin.test.ts`

- Updated imports and comments accordingly

#### Modified: `packages/server/test/daytona-sandbox-provider.test.ts`
- Updated all 47 `yield* SandboxProvider` usages to `yield* DaytonaSandboxProvider`
  since the layer now provides its own tag
- Removed unused `SandboxProvider` import

### Architecture decisions:
- **Routing layer pattern**: The `SandboxProviderRouter` holds both providers as
  internal dependencies and dispatches based on workspace config. This keeps provider
  routing centralized and transparent to `WorkspaceProvider` — it still delegates to
  a single `SandboxProvider` from the Effect context.
- **Optional Daytona**: `DaytonaClient.layer` uses `Effect.fail` (not `Effect.die`) so
  `SandboxProviderRoutedLayer` can catch the error and provide Docker-only. This means
  users without a `DAYTONA_API_KEY` get the exact same Docker experience as before.
- **Provider tags**: Both `DockerSandboxProvider` and `DaytonaSandboxProvider` now provide
  their own tags (not the abstract `SandboxProvider`). The router composes them and
  provides the abstract `SandboxProvider` tag for consumption by `WorkspaceProvider`,
  RPC handlers, and terminal client.
- **Per-workspace dispatch**: For `createSandbox`, the provider is determined by
  `devServerConfig.provider`. For all other operations, the provider is determined
  by the `sandboxProvider` column stored on the workspace in LiveStore. This ensures
  operations always go to the correct provider even after restart.
- **Docker flow unchanged**: The Docker path is completely unaffected. The router
  defaults to Docker for any workspace without an explicit `sandboxProvider` set to
  `'daytona'`. All existing Docker tests pass unchanged (modulo pre-existing
  environment issues with `@effect/vitest` module loading).

## Issue 6: Provider config — global default sandbox provider in appSettings

Status: COMPLETE
Date: 2026-04-07

### Summary:
Most of the infrastructure for Issue 6 was already built in prior issues:
- `defaultSandboxProvider` field in `LaborerConfig` and `ResolvedLaborerConfig` (Issue 5)
- `globalConfig.get` / `globalConfig.update` RPCs with `defaultSandboxProvider` field
- `settings.getDefaultProvider` / `settings.setDefaultProvider` RPCs and handlers
- `SandboxProviderSetting` UI component in `app-settings-modal.tsx` with dropdown
- Config resolution for `defaultSandboxProvider` across config layers

The **missing piece** was the fallback wiring: when `devServer.provider` resolves
to `null` (no per-project provider set), it should fall back to the global
`defaultSandboxProvider`. This completes the resolution precedence chain:
per-project `devServer.provider` > global `defaultSandboxProvider` > hardcoded null (docker).

### Changes made:

#### `packages/server/src/services/config-service.ts`:
- Added `applyProviderFallback` helper function: when `devServer.provider.value`
  is null and `defaultSandboxProvider.value` is not null, constructs a new
  `ResolvedDevServerConfig` with `provider` set from `defaultSandboxProvider`
  (preserving the source provenance metadata)
- Extracted from `mergeConfigs` to keep function complexity under the Biome
  lint threshold (max 20)
- Called at the end of `mergeConfigs` after both `devServer` and
  `defaultSandboxProvider` are resolved, before returning

#### `packages/server/test/config-service.test.ts`:
- Updated test name: "should resolve per-project devServer.provider independently
  from defaultSandboxProvider" → "should let per-project devServer.provider
  override defaultSandboxProvider" (reflects the override semantics)
- Fixed "should return null defaults for provider, resources, autoStopInterval"
  test to back up and clear global config (prevents env-dependent false failures
  when the developer's global config has `defaultSandboxProvider` set)
- Added 3 new tests:
  - Falls back devServer.provider to defaultSandboxProvider when no per-project
    provider is set (global config → devServer.provider)
  - Keeps devServer.provider as null when no defaultSandboxProvider is set
  - Falls back devServer.provider from ancestor defaultSandboxProvider (ancestor
    laborer.json → devServer.provider)

#### `packages/server/test/rpc/config-management.test.ts`:
- Updated 2 integration tests that assert resolved config structure:
  - Excluded `devServer.provider` from deep-equality comparisons (same as
    `defaultSandboxProvider`) since both are env-dependent via the global
    config fallback
  - Added flexible assertions: `devServer.provider.value` must be one of
    `[null, 'docker', 'daytona']` with a valid string `source`

### Design decisions:
- Fallback applied at the `mergeConfigs` level (not at consumption sites like
  `WorkspaceProvider`) because config resolution is centralized and consumers
  should receive the fully resolved value without needing to know about the
  fallback chain
- `applyProviderFallback` uses spread to create a new object (not mutation)
  since `ResolvedDevServerConfig` has `readonly` properties
- Source provenance tracks back to the `defaultSandboxProvider` source (e.g.,
  `~/.config/laborer/laborer.json`) — not marked as "default" — so the UI
  can show users where the provider setting came from
- When both `devServer.provider` and `defaultSandboxProvider` are null, the
  effective provider stays null. Downstream code (`WorkspaceProvider`,
  `SandboxProviderRouter`) already treats null as "docker"
