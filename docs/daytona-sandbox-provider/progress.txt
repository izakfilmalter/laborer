## Issue 8: SandboxProvider Effect interface definition

Status: COMPLETE
Date: 2026-04-07

### Changes made:
- Created new file packages/server/src/services/sandbox-provider.ts
- Defined SandboxProvider Effect Context.Tag with identifier '@laborer/SandboxProvider'
- Interface includes 8 methods:
  createSandbox(params: CreateSandboxParams) => Effect<void, RpcError>
  destroySandbox(workspaceId: string) => Effect<void, RpcError>
  pauseSandbox(workspaceId: string) => Effect<void, RpcError>
  resumeSandbox(workspaceId: string) => Effect<void, RpcError>
  getPreviewUrl(workspaceId: string, port: number) => Effect<string, RpcError>
  spawnTerminal(workspaceId: string, opts?: TerminalOpts) => Effect<TerminalHandle, RpcError>
  reconcileState() => Effect<void>
  checkAvailability() => Effect<ProviderStatus>
- Defined CreateSandboxParams type with workspaceId, branchName, projectName, worktreePath,
  devServerConfig (matching ResolvedDevServerConfig shape), and optional onReady callback
- Defined TerminalOpts type with optional command, autoRun, cols, rows
- Defined TerminalHandle type with id, workspaceId, command, status — matches existing
  TerminalRecord shape from terminal-client.ts for drop-in compatibility
- Defined ProviderStatus type with available boolean + optional error string — matches
  existing DockerStatus shape from docker-detection.ts
- All types exported for use by both Docker and Daytona implementations

### Design decisions:
- CreateSandboxParams.devServerConfig uses concrete types (not ResolvedValue<T> wrappers)
  since providers need the resolved values, not the provenance metadata
- TerminalHandle intentionally matches TerminalRecord to minimize adapter code in Issue 9
- ProviderStatus intentionally matches DockerStatus to minimize adapter code in Issue 9
- No layer defined on SandboxProvider — implementations provide their own layers
- reconcileState and checkAvailability have no error channel (Effect<void> / Effect<ProviderStatus>)
  since failures are handled internally (logged, not propagated)

- bun run format passes

## Issue 9: DockerSandboxProvider — wrap existing ContainerService behind SandboxProvider

Status: COMPLETE
Date: 2026-04-07

### Changes made:
- Created new file packages/server/src/services/docker-sandbox-provider.ts
- Defined DockerSandboxProvider as a Context.Tag that produces a SandboxProvider value
- DockerSandboxProvider.layer depends on ContainerService, DepsImageService, DockerDetection,
  TerminalClient, and LaborerStore
- All 8 SandboxProvider interface methods implemented as thin delegation:
  - createSandbox: orchestrates DepsImageService.ensureDepsImage + ContainerService.createContainer
    (mirrors existing performContainerSetup flow from WorkspaceProvider)
  - destroySandbox: delegates to ContainerService.destroyContainer
  - pauseSandbox: delegates to ContainerService.pauseContainer
  - resumeSandbox: delegates to ContainerService.unpauseContainer
  - getPreviewUrl: constructs http://{sandboxUrl}:{port} from LiveStore workspace data,
    falls back to containerName() utility for URL derivation
  - spawnTerminal: delegates to TerminalClient.spawnInWorkspace (which already handles
    docker exec path for containerized workspaces)
  - reconcileState: no-op — ContainerService.layer already runs startup reconciliation
    + docker events listener as daemon fibers
  - checkAvailability: delegates to DockerDetection.check()

### Design decisions:
- Pure adapter layer: no new behavior introduced, existing Docker flow unchanged
- ContainerService continues to emit v1.Container* events internally (both v1 and v2
  materializers write to the same sandbox* columns, so this is correct)
- Full migration of Docker path to v2 events deferred to Issue 10 (WorkspaceProvider refactor)
- Uses Layer.effect (not Layer.scoped) since no finalizers are needed — cleanup is handled
  by the underlying services (ContainerService, TerminalClient)
- createSandbox looks up project repoPath from LiveStore for lockfile detection, falling
  back to worktreePath if project lookup fails
- getPreviewUrl returns full http:// URL with port appended

## Issue 7: Daytona env vars in packages/env

Status: COMPLETE
Date: 2026-04-07

### Changes made:
- Extended packages/env/src/server.ts with three new Daytona-specific env vars:
  - DAYTONA_API_KEY: optional string (z.string().min(1).optional()) — only required at
    runtime when Daytona provider is actually used, validated by DaytonaClient service
  - DAYTONA_API_URL: optional string with URL validation, defaults to "https://app.daytona.io/api"
  - DAYTONA_TARGET: optional string, defaults to "us"
- All three vars use Zod validation consistent with existing env vars (TERMINAL_GRACE_PERIOD_MS, etc.)
- Variables are loaded via @t3-oss/env-core with emptyStringAsUndefined: true
- .env.local already contains DAYTONA_API_KEY and DAYTONA_API_URL values — now properly
  validated and typed through the env schema

### Design decisions:
- DAYTONA_API_KEY is optional at the schema level (not required) because not every user
  has Daytona credentials. Runtime validation happens in the DaytonaClient service (Issue 11)
  when the provider is actually used
- DAYTONA_API_URL uses z.string().url() for proper URL validation with a sensible default
- DAYTONA_TARGET uses z.string().min(1) (not an enum) to allow future region values without
  schema changes
- No test files added — packages/env has no existing test infrastructure, and env validation
  is tested implicitly by the server test suite which imports the env module
