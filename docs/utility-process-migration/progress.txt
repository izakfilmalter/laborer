## Issue 1: Bootstrap entry point script — COMPLETED

Date: 2026-03-25

### What was done

Created the bootstrap entry point script that all utility processes will use
when forked via `utilityProcess.fork()`. This is the foundational piece that
enables the entire utility process migration.

### Files created

- `apps/desktop/src/utility-process-bootstrap.ts` — Bootstrap script that:
  - Detects utility process context via `process.parentPort`
  - Reads `LABORER_ENTRYPOINT` env var and dynamically imports the service module
  - Sends `{ type: 'ready' }` to parent on successful load

- `apps/desktop/src/utility-process-types.ts` — Shared types for the bootstrap
  protocol (`UtilityProcessReadyMessage`, `UtilityProcessErrorMessage`,
  `UtilityProcessBootstrapMessage`)

  1. Exits with code 1 when process.parentPort is not available
  2. Exits with code 1 and sends error when LABORER_ENTRYPOINT is not set
  3. Sends ready message when entrypoint loads successfully
  4. Sends error message and exits with code 1 when entrypoint fails to load

- `apps/desktop/test/fixtures/dummy-entrypoint.mjs` — Test fixture

### Files modified

## Issue 2: UtilityProcessManager core (fork, kill, restart) — COMPLETED

Date: 2026-03-25

### What was done

Created the `UtilityProcessManager` class that replaces the HTTP-based
`SidecarManager` with Electron's native `utilityProcess.fork()` API and
MessagePort IPC. This is the core infrastructure for the utility process
migration — all subsequent issues depend on it.

### Files created

- `apps/desktop/src/utility-process-manager.ts` — UtilityProcessManager class:
  - `fork(name)`: Forks a utility process using the bootstrap script, creates
    a `MessageChannelMain` pair, sends one port to the utility process on
    spawn, returns the other to the caller
  - `kill(name)`: Kills a process gracefully (Electron's kill() sends SIGTERM),
    with a cleanup timeout for stuck processes
  - `restart(name)`: Kills old process, waits for exit, forks a new one
  - `killAll()`: Kills all tracked processes, suppresses exit handlers
  - `killAllAndWait(timeout)`: Kills all and waits for exit or timeout
  - `getPort(name)`, `getPid(name)`, `isRunning(name)`, `getLastStderr(name)`
  - `setExitHandler()`: Registers callback for unexpected exits
  - Environment construction: deep-clones process.env, strips dangerous vars
    (ELECTRON_RUN_AS_NODE, ELECTRON_RENDERER_PORT, DEBUG), sets
    LABORER_ENTRYPOINT
  - stdout/stderr captured via readline createInterface into ring buffer
  - Bootstrap protocol messages (ready/error) logged from 'message' event

- `apps/desktop/test/utility-process-manager.test.ts` — 35 unit tests across
  7 describe blocks:
  - fork(): 10 tests (MessagePort creation, bootstrap path, env vars, stdio,
    service name, port transfer on spawn, PID tracking, duplicate kill,
    entrypoint resolution)
  - kill(): 4 tests (running process, no-op for unknown, already-exited,
    intentional stop suppresses exit handler)
  - restart(): 2 tests (kill+fork, works without existing process)
  - killAll(): 2 tests (kills all, suppresses exit handlers)
  - killAllAndWait(): 3 tests (waits for exit, timeout, empty list)
  - unexpected exit handling: 4 tests (fires handler, suppressed on kill,
    suppressed on killAll, includes stderr)
  - MessagePort lifecycle: 3 tests (port closed on exit, getPort, undefined)
  - isRunning(): 4 tests (before spawn, after spawn, after exit, unknown)
  - bootstrap messages: 2 tests (ready, error)

### Files modified

- `apps/desktop/src/utility-process-types.ts` — Added `PortTransferMessage`
  and `UtilityProcessParentMessage` types for the port transfer protocol
  (parent -> utility process direction)

- `apps/desktop/src/main.ts` — Wired UtilityProcessManager into app lifecycle:
  - Import and instantiate alongside existing SidecarManager (coexist during
    migration)
  - Created on `app.whenReady()` in production mode
  - `killAll()` called in shutdown handler on `before-quit`
  - `getUtilityProcessManager()` export for external access
  - Restart handler checks utility process manager first, then falls back to
    health monitor / sidecar manager

### Verification

- TypeScript: no errors
- Biome formatting: no new errors
- No changes to existing test behavior

## Issue 3: MessagePort Effect RPC transport (server side) — COMPLETED

Date: 2026-03-25

### What was done

Created the server-side MessagePort RPC transport that provides an
`RpcServer.Protocol` implementation over MessagePort. This replaces
`RpcServer.layerProtocolHttp({ path: '/rpc' })` in utility process entry
points. The transport uses structured clone via `postMessage()` — no JSON
serialization layer (`RpcSerialization.layerJson`) is needed.

The implementation follows the `withRun` pattern from Effect RPC internals,
using `RpcServer.Protocol.make(Effect.fnUntraced(function*(writeRequest) {...}))`
to create a protocol that:
- Bridges sync MessagePort event listeners to the Effect runtime via an
  unbounded queue drained by a scoped fiber
- Supports a generic `RpcMessagePort` interface that works with Electron
  `MessagePortMain`, Node.js `worker_threads.MessagePort`, and Web
  `MessagePort`
- Handles point-to-point connections (single client ID = 0)
- Supports `ArrayBuffer` transfer for zero-copy data (supportsTransferables)
- Cleans up listeners and closes the port on scope finalization

### Files created

- `packages/shared/src/rpc-transport-messageport.ts` — Server-side transport:
  - `RpcMessagePort` interface: minimal abstraction covering Electron, Node.js,
    and Web MessagePort APIs
  - `makeProtocolMessagePort(port)`: creates an `RpcServer.Protocol` from a port
  - `layerProtocolMessagePort(port)`: Layer wrapper for easy composition
  - Message flow: port.on('message') → Queue.unsafeOffer → fiber drains
    queue → writeRequest(clientId, data) → RPC handler pipeline
  - Response flow: RPC handler → send(clientId, response) → port.postMessage()

- `packages/shared/test/rpc-transport-messageport.test.ts` — 7 unit tests:
  1. Handles echo request/response
  2. Handles add request/response
  3. Propagates RPC errors
  4. Handles streaming RPC (count 0..4, verifies Chunk + Exit messages)
  5. Handles multiple concurrent requests
  6. Handles unknown RPC tag (returns Defect)
  7. Cleans up when scope is closed

### Files modified

- `packages/shared/package.json` — Added export for
  `./rpc-transport-messageport` pointing to the new module

### Verification

- All 82 shared package tests pass (75 existing + 7 new)
- TypeScript: no errors
- Biome formatting: no new errors (pre-existing issues in .opencode/package.json
  and laborer.json are unrelated)

### Acceptance criteria checklist

- [x] A module exports an Effect Layer that serves an RPC group over a
      MessagePort
- [x] The adapter receives a `MessagePort` and handles incoming RPC request
      messages
- [x] Request/response RPC works: client sends a request message, server

- [x] Streaming RPC works: server sends multiple messages for a single request

## Issue 4: MessagePort Effect RPC transport (client side) — COMPLETED

Date: 2026-03-25

### What was done

Created the client-side MessagePort RPC transport that provides an
`RpcClient.Protocol` implementation over MessagePort. This replaces
`RpcClient.layerProtocolHttp({ url })` in the renderer. The transport uses
structured clone via `postMessage()` — no JSON serialization layer
(`RpcSerialization.layerJson`) or `FetchHttpClient.layer` is needed.

The implementation mirrors the server-side transport, using
`RpcClient.Protocol.make(Effect.fnUntraced(function*(writeResponse) {...}))`
to create a protocol that:
- Bridges sync MessagePort event listeners to the Effect runtime via an
  unbounded queue drained by a scoped fiber
- Reuses the `RpcMessagePort` interface from the server-side transport
- Sends `FromClientEncoded` requests via `port.postMessage()`
- Receives `FromServerEncoded` responses via the message listener
- Wraps send errors as `RpcClientError` with reason 'Protocol'
- Supports `ArrayBuffer` transfer for zero-copy data (supportsTransferables)
- Cleans up listeners and closes the port on scope finalization

### Files created

- `packages/shared/src/rpc-transport-messageport-client.ts` — Client-side
  transport:
  - `makeClientProtocolMessagePort(port)`: creates an `RpcClient.Protocol`
    from a port (scoped effect)
  - `layerClientProtocolMessagePort(port)`: Layer wrapper for easy composition
  - Message flow: client calls RPC → send(request) → port.postMessage() →
    server processes → server posts response → port.on('message') →
    Queue.unsafeOffer → fiber drains queue → writeResponse(data) →
    RPC client pipeline delivers result

- `packages/shared/test/rpc-transport-messageport-client.test.ts` — 7 tests
  using end-to-end client+server pairs over Node.js `MessageChannel`:
  1. Handles echo request/response
  2. Handles add request/response
  3. Propagates RPC errors (TestRpcError surfaces as Left)
  4. Handles streaming RPC (count 0..4, verifies collected values)
  5. Handles multiple concurrent requests (3 parallel RPCs)
  6. Handles port disconnection gracefully
  7. Cleans up when scope is closed

### Files modified
